# Online repository — Phase 7

ATMERA is developed and verified in [FUREQ-DEVELOP/RenderingWorkspace](https://github.com/FUREQ-DEVELOP/RenderingWorkspace). That repository already references [FUREQ-DEVELOP/RenderingLibrary](https://github.com/FUREQ-DEVELOP/RenderingLibrary) through `SDK/RenderingLibrary`, but the current solution builds from workspace source. RenderingLibrary is for completed SDK distribution and release assets, without buildable implementation source. The Module Framework remains optional and independent of Graphics and Studio.

`Tools/SearchModules.ps1` is the first repository slice. It uses the signed-in GitHub CLI account to list published releases in RenderingLibrary and returns a JSON array of module ID, version, tag, prerelease flag, and publication time. Releases tagged `module-<id>-v<major>.<minor>.<patch>` appear in search; other SDK releases and drafts do not. `-Query` matches the module ID or release name without case sensitivity. `-Limit` controls how many recent releases are inspected, from 1 to 1000. This is a development tool, not an SDK runtime dependency.

Run `gh auth status` and confirm `fureq-dev` is active, then run `./Tools/SearchModules.ps1 -Query bloom`. As of 2026-11-28, RenderingLibrary has no releases, so the expected result is `[]`. `./Tools/TestSearchModules.ps1` checks filtering and empty results using an offline CLI stub.

`Tools/DownloadModule.ps1 -ProjectRoot <project> -ModuleId <id> -Version <major.minor.patch>` expects a published release with tag `module-<id>-v<version>` and two assets: `<id>-<version>-win-x64.dll` and `<id>-<version>-win-x64.dll.sha256`. The sidecar contains only the DLL's 64-character hexadecimal SHA-256 digest. The tool checks the release tag and asset names, downloads into a temporary directory under the project's `Downloads/<id>/`, verifies the digest, and moves the directory to `Downloads/<id>/<version>/` only after validation. It refuses existing versions and redirected download directories. A failed download or hash check removes the temporary directory. By default it returns the verified DLL path without installing or loading it.

After building `ATMERA.sln`, add `-Action Install` to register a new module, or `-Action Update` to replace a selected version. `-Configuration Release` selects the Release build of `ATMERA.ModuleTool.exe`; Debug is the default. The tool calls the existing Module Framework installer, which checks the Plugin ABI and reported module ID and writes the project-local `Modules.lock`. The downloaded file remains available if installation fails; the selected installed version is preserved by the Module Framework. For example: `./Tools/DownloadModule.ps1 -ProjectRoot C:\Projects\Example -ModuleId atmera.example -Version 1.2.3 -Action Install`.

`./Tools/TestDownloadModule.ps1` verifies download and hash-mismatch cleanup with an offline CLI stub. `./Tools/TestRepositoryInstall.ps1` uses actual test DLLs to verify install, update, and rejection of a mismatched Plugin ABI ID. Both run through `Tools/Test.ps1`. No actual release exists yet, so the live download path has not been exercised.

The remaining Phase 7 work is a public runtime repository API and a real release download check. No downloaded DLL should be loaded before its identity and hash are checked. A release tag and its sidecar hash are discovery and integrity metadata, not independent proof of publisher identity. The workspace repository must not become a shared module installation directory.
