# Module specification

The module runtime is the optional, graphics-independent Module Framework boundary. ATMERA basic rendering does not require module registration, an `Engine`, or a project manifest. Graphics modules may opt into this framework later; game-engine modules are outside ATMERA's product roadmap.

Modules are project-scoped. Phase 1 registers `ModuleSpec` values programmatically with module ID, DLL path relative to the project's `Modules/` directory, dependency IDs, and enablement. The runtime rejects duplicate IDs, missing or disabled dependencies, dependency cycles, paths outside `Modules/`, absent DLLs, and exported IDs that differ from the registered ID. Active modules initialize in dependency order and shut down in reverse order. Startup failure unloads modules already started, removes their services and subscriptions, and allows a later retry. `ModuleState` exposes discovery, validation, resolution, loading, initialization, activation, deactivation, shutdown, unload, and failure states.

An `Engine` instance is bound to one project root and contains only module-hosting services; it does not own a graphics device. It is built in `ATMERA.ModuleFramework.lib`. The class name remains for source compatibility; its responsibility is the module host, not a game engine. Switch projects by stopping and destroying the previous instance, then constructing an instance for the next project. Individual runtime DLL hot unload is not supported. Manifest parsing, version pinning, and package installation belong to the project package phase. Future manifests will declare version, ABI compatibility, platform, architecture, and optional GPU capabilities.
